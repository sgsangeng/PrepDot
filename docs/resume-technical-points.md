## 一、Java 后端

### 核心能力
- ✅ 基于 Spring Boot 3.3.4 + MyBatis-Plus + MySQL 8 独立设计并实现 RESTful API 服务，覆盖用户认证、卡组/卡片管理、复习计划调度、AI 生成代理等模块
- ✅ 设计多层级数据模型（卡组自引用外键 + depth 字段实现有限层级结构），支持 AI 生成的"大主题→小主题"两级卡组
- ✅ 文件解析：Apache PDFBox（PDF）+ Apache POI（docx/pptx）多格式文本抽取
- ✅ 用 `java.net.http.HttpClient` 手写 AI 服务调用封装，区分 connectTimeout（建连超时）与整体 timeout（响应超时）两级超时控制

### 鉴权与安全（最值得深挖的一块）
- ✅ 从"各 Controller 手写、部分接口完全无鉴权"重构为统一的 Servlet Filter 鉴权链路（`JwtAuthFilter` + `@Order` 保证执行时序）
- ✅ 基于 `ThreadLocal` 实现请求级用户上下文（`UserContext`），并通过 `try/finally` 强制清理，规避 Tomcat 线程池复用导致的跨用户身份串号风险
- ✅ 设计携带 HTTP 状态码的业务异常体系（`BusinessException` + `GlobalExceptionHandler`），替代此前统一返回 400 的裸 `RuntimeException`
- ✅ 排查并修复多处越权访问（IDOR）漏洞：卡片增删改接口缺失归属校验、复习评分接口可篡改他人卡片记忆度、社区卡包导入未正确归属用户
- ✅ 有真实的故障排查故事支撑：从"AI 生成卡组在客户端不可见"这一真实 bug 出发，定位到根因是请求漏带 token、后端"宽松放行"策略导致脏数据，进而系统性重构了整条鉴权链路

### 待补充的性能与工程化项（可作为"已识别的技术债"来讲，体现工程判断力）
- 🔷 N+1 查询问题（卡组列表接口为每个卡组单独查询卡片来计算聚合统计）
- 🔷 Redis 缓存设计（今日计划、卡组列表这类读多写少数据，含缓存失效策略设计）
- 🔷 AI 生成接口异步化（当前同步阻塞 Tomcat 工作线程最长 120 秒，计划改为独立线程池隔离 + 任务状态轮询）
- 🔷 并发安全（`daily_plan.completed_count` 当前是非原子的"查询-修改-写回"，计划改为数据库原子自增）
- 🔷 单元测试覆盖（目前仅算法模块有测试，计划扩展到权限校验等逻辑密集区域）

## 二、记忆算法（FSRS-4.5）

- 🔶 将复习评分算法从"固定加减分规则"升级为 **FSRS-4.5**——Anki 自 2023 年起默认使用的间隔重复算法（比 SM-2 更新、更被业界认可），用 Difficulty（难度）、Stability（稳定性）、Retrievability（可提取性）三个连续变量对每张卡片的记忆状态单独建模
- ✅ 核心算法模块（`com.prepdot.algorithm`）完全独立于 Spring/数据库，纯函数实现，采用 TDD（先写测试再写实现）方式开发
- ✅ 针对含 `exp`/`pow` 的复杂数学公式，设计了区别于普通业务代码的测试策略：不变量测试（如"成功复习后稳定性绝不会下降"）+ golden master 回归测试（先跑真实输出锁定基准，防止后续改动破坏行为），而非依赖手算数值做精确断言
- ✅ 能清楚讲解模型的数学自洽性——当目标保留率设为 90% 时，下次复习间隔在数值上必然等于当前稳定性，这是算法设计的内在恒等式而非巧合
- 🔶 接入真实读写路径：复习提交（`submitReview`）按 FSRS 更新难度/稳定性/下次间隔；今日计划、卡组列表、卡组平均记忆度三处读接口改为查询时实时计算记忆度（而非存储静态过期值）
- ✅ 对算法边界有清晰认知，能讲清楚"做了什么"与"有意不做什么"：未做个性化参数优化（未按用户历史拟合专属权重，用的是官方默认权重）、未做知识图谱增强记忆传播、目标保留率固定 90% 未做成用户可调参数——这些是范围控制决策，不是能力缺口

**面试高频追问预案**：
- "为什么不用更简单的 SM-2？" → FSRS 是基于千万级真实 Anki 复习数据用 MLE 训练出的公开算法，比 SM-2 单一的 ease factor 标量更精细，用连续的幂函数遗忘曲线显式建模"多久没复习会忘"
- "这是你自己实现的还是接的第三方库？" → 手写 Java 实现，不是直接引入现成库，这样才能讲清楚每一步公式的推导依据

## 三、Agent 工程能力

> ⚠️ 这一整块目前是**设计完成、代码即将开始写**的状态。如果投递时还没落地，建议写成"设计并主导实现"而不是过去式的"已完成"，面试前务必确认真实进度，避免被问到实现细节时露馅。

### 架构设计
- 🔷 设计并实现可复用的 Agent 编排层（而非为每个 AI 功能单独写一套调用逻辑）：
  - `AgentTool` 工具抽象接口 + `ToolRegistry` 工具注册与分发机制
  - 手写 **ReAct（Reasoning + Acting）循环**（不依赖 Spring AI / LangChain 等框架），基于 DeepSeek 的 OpenAI 兼容 function calling API 实现模型自主决策"是否调用工具、调用哪个、传什么参数"
  - Agent 执行轨迹持久化（`agent_run`/`agent_step` 表），支持完整回放某一次 Agent 决策链路——这是"Agent 可观测性"能力，很多同类项目会忽略的一块
- 🔷 **Generator + Critic 自我修正循环**：AI 生成内容后先经过审查员（Critic）按质量标准检查（分类多样性、答案空洞度、重复检测），不合格则携带审查意见打回重新生成，最多重试 N 次——这是简化但真实的多 Agent 协作模式
- 🔷 两个不同的 Agent 任务共用同一套编排基建（卡片生成 Agent + 学习教练 Agent），证明架构是真正可复用的，不是一次性脚本

### 具体落地：AI 学习教练
- 🔷 基于用户 FSRS 记忆状态数据（而非旧的固定分数）设计诊断工具集：查薄弱卡片（按 stability 排序）、查复习趋势统计、查卡组冷落情况
- 🔷 支持"诊断→（模型自主判断）生成针对性补充卡片"的完整链路，生成部分复用 Generator+Critic 质检流水线
- 🔶 有真实问题驱动这个设计的动机：发现 AI 批量生成卡片时 `category` 字段大量雷同（同一批卡片全部落在同一个笼统分类下），导致知识图谱失去区分度——这直接催生了"自我修正循环"的设计，不是凭空想的功能

**面试高频追问预案**：
- "你说的 Agent 和普通调 API 有什么区别？" → 普通调用是"一次输入一次输出"，没有决策；这里模型在 ReAct 循环里自主判断下一步该调用哪个工具、要不要继续，这是真正的多步决策，可以用 `agent_step` 表里记录的真实轨迹举例说明
- "为什么不用现成的 Agent 框架？" → 项目规模不需要框架的复杂度，手写能完全掌控每一步的执行细节和面试可讲解性；如果用框架，工具调用的具体机制会变成黑盒

## 四、产品设计与需求思维

- ✅ 主导产品文档从最初"本地优先桌面应用"（Next.js + Tauri + SQLite）构想，迭代为实际交付的"iOS 原生客户端 + Spring Boot 后端服务"架构，并针对这次方向调整完整复盘了技术选型的取舍依据
- ✅ 多轮基于真实使用反馈的交互迭代，能讲清楚"为什么改"：
  - 知识图谱从半高弹窗改为全屏页面——因为图谱需要拖拽缩放等沉浸式空间操作，弹窗形态和操作诉求冲突
  - 复习卡片背面改为"问题(次要样式)+答案(主要样式)"同屏显示，而非翻面后问题完全消失——复习时经常需要对照问题回看答案，完全隐藏会打断学习心流
  - 知识图谱连线从贝塞尔曲线改为直线、每卡组独立成图而非全部挤在一张图——早期版本视觉纠缠不可读，用户反馈后针对性简化
- ✅ 具备"识别问题→排优先级→给出取舍理由"的技术决策能力：面对鉴权漏洞、性能债、算法债、Agent 能力等多条待办线，能按"安全 > 可验证的核心能力 > 性能 > 测试"这样的优先级排序并说明依据，而不是眉毛胡子一把抓
- ✅ 能诚实评估当前方案的局限并给出下一步方向（比如固定 delta 算法升级到 FSRS 的动机、学习教练诊断依赖真实记忆状态数据而非旧分数的原因）——这种"知道自己在哪个阶段"的判断力本身就是产品/工程综合能力的体现
